# Memory Lab Demo V2 改进方案

- 日期：2026-11-24
- 工作区：`E:\memory_demo`
- 状态：待用户确认；本次仅编写方案，尚未修改实现。

## 1. 改进目标与范围

将目前的“保存记忆 → 新会话测试 → 最后比较”改为“直接聊天 → 自动形成记忆 → 随时新开会话验证”。

| 用户提出的改进 | 本次拟实现的行为 |
| --- | --- |
| 四层记忆不用 SQLite | 使用 JSONL 原始记录、JSON 记忆笔记和版本索引、Markdown 主题知识库、JSON 上下文快照 |
| 不再手动点击“保存一份记忆” | 用户正常发送消息，agent 自动识别值得保留的重点，校验后自动更新记忆 |
| Deep Agents 进入实际会话 | 可直接使用 Deep Agents 聊天、自动记忆、新开会话调用记忆；并排比较作为一种聊天模式 |
| 界面更简明 | 一个聊天主界面，保留新会话、引擎选择、是否使用历史记忆；技术细节按需展开 |

范围覆盖热量选餐模块及其共享记忆、会话、运行轨迹基础设施。原交互演示的记忆底座一并适配文件存储，历史材料可继续回查。现有热量计算、只读 SQL、菜品核验和引用追踪能力保留。

### SQLite 的边界

本方案把“不使用 SQLite”落实到**记忆、会话、运行事件、索引和 Deep Agents 检查点**。迁移后，这些功能不再依赖 SQLite 文件。

当前饭菜业务库 `data/meal_lab/meal_catalog.sqlite3` 用于多表 SQL 查询和热量计算，属于业务数据。本方案暂保留该独立业务库及只读查询能力，不修改其他 DBeaver 数据库。

因此，验收目标是“记忆与会话文件化”，并非“删除项目内所有 SQLite 文件”。若还要更换饭菜业务库的数据库类型，应在开发前另行调整该项范围。

## 2. 新的使用流程

1. 打开页面，直接输入自然语言，例如：“以后午饭别给我推荐辣的，预算73块，热量控制在470到610千卡。”
2. agent 回答当前问题，同时自动识别、整理并保存可复用的偏好。
3. 消息旁显示简短状态：“已记住：午饭不辣、预算73元、470～610千卡。”用户不需要命名记忆或点击保存。
4. 点击“新会话”，默认沿用该记忆空间、该引擎的长期记忆；只输入：“明天中午吃什么好？”
5. 查看回答是否沿用之前的偏好。需要解释时展开“本次使用的记忆”，查看原话、笔记、知识库和实际上下文。
6. 新建“无历史记忆”会话，问同一句话，作为对照。
7. 选择 Deep Agents 单独聊天，或从第一轮就使用“并排对话”，测试其完整记忆形成与跨会话使用过程。

默认流程移除“保存一份记忆”“先提取再整理”等前置操作。旧记忆版本选择收纳到详情中，用于回溯实验，不作为正常聊天的必经步骤。

## 3. 四层记忆如何存成文件

### 3.1 目录结构

拟新增独立目录，避免直接覆盖现有数据：

```text
E:\memory_demo\data\memory_v2\
  workspaces\<space_id>\
    workspace.json                      空间信息与格式版本
    sessions\
      index.json                        会话目录
      <session_id>.json                 引擎、记忆策略、会话绑定信息
    four_layer\
      transcripts\<session_id>.jsonl    L1：原始消息与工具原始结果
      notes\<note_id>.json              L2：不可变的事实与偏好笔记
      knowledge\index.md               L3：主题目录
      knowledge\topics\*.md            L3：当前主题知识
      knowledge\revisions\...           L3：历史主题版本
      versions\<version_id>.json        记忆版本及对象引用清单
      heads.json                        当前有效笔记、主题和版本索引
      contexts\<turn_id>\*.json         L4：本轮实际上下文快照
    deep_agents\
      AGENTS.md                         Deep Agents 的长期记忆入口
      knowledge\*.md                    按需读取的主题记忆
      transcripts\<session_id>.jsonl    本引擎的原始会话记录
      revisions\...                     记忆文件历史版本与变更记录
      checkpoints\<session_id>\...      文件化会话执行检查点
      manifest.json                     文件、版本与来源索引
    runs\<run_id>\
      run.json                          任务状态、结果、时间、用量
      events.jsonl                      真实模型请求、响应及工具事件
      evidence\...                      SQL 证据与结果展示材料
```

JSON 使用 UTF-8，JSONL 按记录追加；Markdown 便于直接用编辑器检查。运行记录标识所属引擎，避免将两套引擎的回答或记忆混用。

### 3.2 每层的职责

| 层次 | 格式 | 保存内容 | 如何引用 |
| --- | --- | --- | --- |
| L1 原始记录 | JSONL | 用户消息、回答、工具结果，带消息ID、会话ID、时间和引擎标识 | 通过消息ID定位原话 |
| L2 记忆笔记 | JSON | 记忆内容、类型、主题、作用范围、原文摘录、来源ID、版本及有效状态 | 笔记引用 L1 消息ID和逐字摘录 |
| L3 记忆表示 | Markdown + JSON 索引 | 饮食偏好、表达习惯、明确事实等主题页及目录 | 主题页链接具体笔记ID和版本 |
| L4 注入上下文 | JSON | 本轮实际使用的记忆、当前问题、当前会话历史、检索结果及模型请求关联 | 记录使用了哪些原文、笔记与主题版本 |

L4 每轮独立组装。只用于结果展示的材料继续标记为 `sent_to_model=false`，不能把它冒充已经发送给模型的内容。

### 3.3 笔记示例

以下为拟定格式示意，开发时再固定完整字段约束：

```json
{
  "id": "N-example-001",
  "type": "preference",
  "topic": "meal",
  "scope": {"meal_period": "lunch", "lifetime": "persistent"},
  "key": "max_spice",
  "value": 0,
  "content": "午饭不吃辣",
  "evidence": [{
    "message_id": "T-example-001",
    "quote": "以后午饭别给我推荐辣的"
  }],
  "version": 1,
  "supersedes": null,
  "status": "active"
}
```

保留现有来源ID及引用链思路。内容修改产生新笔记和新版本，不覆盖历史证据。

### 3.4 文件一致性与恢复

- 单进程演示下，对同一空间的记忆写入串行处理；agent 文件修改也纳入同一空间的写入管理。
- JSON 及索引使用临时文件写入后原子替换；JSONL 追加后记录完成状态。
- 一次记忆更新先写对象和主题版本，最后发布版本清单与当前版本指针；读取只使用完整提交的版本。
- 消息和任务使用稳定ID，重复发送或失败重试不能重复形成相同记忆。
- 索引可由已提交记录重建；不完整任务、截断记录和未发布版本要能识别，不能误显示成功。

## 4. 聊天时自动形成记忆

### 4.1 每轮处理链路

```text
用户发送消息
  → 记录原话并固定本轮历史记忆版本
  → 识别当前需求、可复用重点、临时要求与纠正
  → 按主题检索相关记忆，组装本轮上下文
  → agent 回答；选餐时继续调用只读 SQL 并核验结果
  → 校验并自动提交本轮记忆变化
  → 展示回答、记忆变化状态、耗时和 token
```

本轮明确要求优先应用；只有通过校验的重点才提交为后续可复用记忆。返回完成状态前，应明确本轮记忆是已保存、无变化还是保存失败，避免界面先显示“已记住”而实际仍未落盘。

### 4.2 自动记忆规则

| 用户输入示例 | 处理方式 |
| --- | --- |
| “我不吃辣。” | 自动记录明确的口味偏好 |
| “以后午饭预算73块，热量470到610千卡。” | 按午饭范围记录预算和热量目标 |
| “我家猫叫年糕。” | 作为有原话依据的明确事实保存，不局限于选餐字段 |
| “以后回答简短一点。” | 作为表达偏好保存 |
| “今天想吃辣，预算200。” | 本轮临时覆盖，不覆盖长期不辣偏好 |
| “以后预算改成80元，其他不变。” | 更新预算版本，保留同一作用范围内的其他有效条件 |
| “晚饭预算500，喜欢辣。” | 与午饭分开记录；明确偏好没有临时限定时，按餐次形成可复用记忆并展示记忆摘要 |
| “这条别作为长期偏好。” | 不生成或撤销对应长期笔记；原始对话与长期记忆分开处理 |
| “晚上吃什么好？” | 优先读取已有偏好；提问本身不构成新的口味、预算或热量记忆 |
| 含糊、否定关系不明确、互相冲突的说法 | 不猜测写入；必要时通过一句自然追问澄清 |

普通闲聊不强行生成笔记，agent 自己给出的建议不自动当成用户事实。用户可以在记忆详情中纠正或撤销，但不需要逐条手动审批保存。

原话摘录、数值、餐次、长期/临时范围继续校验。例如“喜欢辣”与“能吃辣”分开，“不超过1000千卡”不能自动补出旧的热量下限。

### 4.3 新会话与无记忆对照

- 新会话默认读取同一空间、同一引擎最新已提交的长期记忆，不复制旧聊天全文。
- 同一会话继续聊天时，允许读取该会话自己的历史。
- 新会话发起前必须处理好前一轮的记忆提交状态，防止“刚说完就新开会话”漏记。
- 无记忆对照固定为“不读长期记忆、不写长期记忆”；当前会话仍能正常聊天。
- 无记忆模式不能通过后备检索、旧版本指针、Deep Agents 的 AGENTS.md 或其他缓存重新取得长期偏好。
- 缺少偏好时不冒充“记得用户要求”。业务查询若采用演示默认值，必须明确标识为默认值。

## 5. Deep Agents 作为正式聊天引擎

### 5.1 三种可选模式

| 模式 | 正常对话行为 | 新会话行为 |
| --- | --- | --- |
| 四层记忆 | 自动维护 L1～L4，检索相关记忆并回答 | 使用本引擎的文件化长期记忆 |
| Deep Agents | 真实框架执行，自动读取、维护 AGENTS.md 和主题文件，调用业务工具 | 使用本引擎已形成的文件记忆，创建新的会话检查点 |
| 并排对话 | 同一条用户消息分别交给两套引擎，分别回答、更新记忆并统计 | 两组各自使用自己的长期记忆和新的会话 |

默认使用四层记忆；Deep Agents 可单独选择。切换引擎通过新建会话完成，保留旧会话，不把已有聊天线程偷偷改成另一引擎。

### 5.2 独立形成记忆

- 两套引擎使用独立目录、长期记忆、运行状态与版本索引。
- Deep Agents 从用户原话学习并维护自己的文件，不直接把四层笔记复制成它的记忆，也不由后端把标准答案写进 AGENTS.md 后声称模型记住了。
- Deep Agents 的记忆写入同样需要来源、作用范围和版本校验；原始文件变更及校验失败均保留。
- 某个空间若只在四层引擎中聊过，首次进入 Deep Agents 时应如实显示该引擎尚无历史记忆。
- 要公平观察同一批对话的学习效果，推荐从第一轮选择“并排对话”。历史资料初始化时，只能向两组提供相同的用户原话，且明确记录初始化学习的调用及用量。

### 5.3 移除 SQLite 检查点

Deep Agents 目前使用的 `learning.sqlite`、`fresh-checkpoints.sqlite` 等检查点也需要替换，不能仅把长期记忆正文改成 Markdown。

拟实现与当前框架兼容的文件检查点存储，保存线程状态、消息、工具调用关联和执行进度。需要验证同会话继续聊天、工具调用、重启恢复与新会话隔离；不能只保存最终回答来代替检查点。

新会话不加载旧线程检查点，只读取允许使用的长期记忆。正常聊天过程中就产生记忆，不再依赖最后一次“比较”才开始学习。

### 5.4 热量与 SQL 仍可核验

两套引擎使用相同的业务工具、热量公式、数据快照和结果核验口径。保留辣度、预算、热量、推荐去重、候选遗漏及无符合项检查。

核验器的期望依据来自用户明确原话与业务规则；不得把四层引擎内部笔记当作 Deep Agents 必须照抄的上下文。若发生参数拦截、检索原话或重试，仍如实展示。

## 6. 简化后的聊天界面

主界面保留一个聊天工作区，取消默认三步表单：

```text
┌─────────────────────────────────────────────────────────┐
│ 新会话  引擎：四层 / Deep Agents / 并排  使用历史记忆：开/关 │
├─────────────┬───────────────────────────────────────────┤
│ 最近会话     │ 对话消息                                  │
│             │ 用户：以后午饭不吃辣，预算73块……             │
│ 会话1        │ agent：……                                │
│ 会话2        │ 已记住：午饭不辣、预算73元…… [查看记忆]       │
│             │                                          │
│             │ 输入消息……                         [发送] │
└─────────────┴───────────────────────────────────────────┘
```

交互约定：

- 默认只显示会话列表、聊天区及必要状态，不常驻多层卡片、SQL编辑器和大段架构说明。
- 历史记忆开关属于会话级设置。更换引擎或历史记忆策略时创建新会话，并明确显示实际生效状态，避免“下拉选项变了，但还在用旧会话”。
- 记忆状态仅用一行表达：“已记住”“已更新”“本轮不写长期记忆”“记忆更新失败”。详细原因放在展开内容。
- 回答下显示本轮耗时和实际 token；并排模式两组分别展示。
- “查看记忆”打开详情抽屉：四层引擎查看四层及来源，Deep Agents 查看 AGENTS.md、主题文件、变更与本轮实际加载内容。
- SQL、数据库结构、公式明细、完整轨迹收纳到“高级详情”。需要时可检查，默认不干扰聊天。
- 没有历史记忆、没有保存内容、请求失败或正在运行时，都给出可执行的状态提示，不只留下一个灰色按钮。
- 桌面端并排模式双列显示；窄屏上下排列，保留浏览器缩放能力，防止右侧被裁切。

## 7. 运行统计与可观察性

每轮分别记录：

- 本轮输入、所用历史记忆版本、实际读取与实际注入的来源ID。
- 本轮新增、更新、撤销或忽略了哪些记忆，是否提交成功。
- 记忆读取、模型处理、业务查询、记忆写入及整轮总耗时。
- 服务端实际返回的输入、输出、总 token；未提供时明确显示，不估算冒充。
- 自动提取、文件整理、重试和纠错产生的模型调用，一并计入本轮用量。

并排模式两组收到相同的用户输入，使用独立记忆和线程，分别计时。框架提示词、记忆维护方式与调用次数不同，因此展示实验记录，不做等预算性能排名。

## 8. 旧数据迁移

1. 为现有记忆库、Deep Agents 文件和索引建立迁移前备份及清单。
2. 只读导出旧 SQLite 的原话、笔记、主题、上下文、会话、运行及事件到新目录，保留来源ID、时间与版本关联。
3. 保留原空间和会话绑定；新入口根据原会话选定的版本恢复，不把互相冲突的历史版本合并成一套偏好。
4. 已有 Deep Agents 文件按原空间、来源版本导入；来源不明的旧文件仅作为历史资料，不伪装成当前引擎已学习的记忆。
5. 校验对象数量、引用可解析性、会话绑定及抽样内容；通过后切换新运行存储。
6. 旧 SQLite 保留为归档，不删除、不继续承担运行时读写，也不在文件读取失败时静默回退到旧库。

迁移需可重复执行且不重复导入。失败时保持现有版本可运行，不能覆盖后只留下不完整文件。

## 9. 开发落地顺序

| 阶段 | 主要工作 | 完成证据 |
| --- | --- | --- |
| 1. 文件存储与迁移 | 抽出存储接口，实现文件存储、索引、版本及导出工具 | 保存、读取、引用、重启恢复及迁移校验通过 |
| 2. 四层自动记忆聊天 | 新增统一聊天处理，识别重点、区分临时/长期、自动提交记忆 | 不点击保存即可跨会话记住偏好与明确事实 |
| 3. Deep Agents 日常接入 | 正常对话、文件记忆维护、文件检查点及独立会话策略 | 单独聊天和新会话均能使用其自主形成的记忆 |
| 4. 新聊天前端 | 聊天区、会话列表、引擎选择、记忆详情、统计 | 默认界面无需三步表单，操作状态与实际会话一致 |
| 5. 并排模式与回归 | 两引擎独立学习、同题回答，保留 SQL、引用及对照核验 | 完整真实模型演示及关键回归通过 |

预期涉及 `store.py`、`engine.py`、会话管理、`meal_engine.py`、Deep Agents 适配与比较逻辑、API 和 React 聊天组件。具体文件拆分在开发时依据现有调用链确定，避免只改前端按钮、底层仍依赖旧流程。

## 10. 验收场景

| 场景 | 操作 | 必须达到的结果 |
| --- | --- | --- |
| 文件存储 | 正常聊天、更新记忆、查询和重启 | 新记忆目录不生成 SQLite；原话、笔记、主题、上下文、轨迹及检查点均可回查 |
