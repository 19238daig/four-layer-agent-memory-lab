# 热量选餐、SQL 与四层记忆

本场景在现有 React 页面中增加“热量选餐实验室”。所有日常演示均通过前端按钮执行。

## 简明界面：三步演示

打开 <http://127.0.0.1:8010/?view=meal>，默认只显示三个步骤，原有记忆和会话继续保留。

1. **保存一份记忆**：名称填写“我的午饭偏好”，输入“我不吃辣，午饭预算73块，热量尽量控制在470到610千卡。”，点击“保存这份记忆”。保存名称与偏好一次完成。
2. **新会话测试**：选择刚保存的记忆，点击“新开会话并加载”。只问“明天中午吃什么比较合适？”，点击“测试它是否记得”。程序自动生成并执行只读SQL，展示回答、实际条件和“选定记忆已生效”的核验结果。无需手动执行SQL。
3. **Deep Agents 对比**：点击“开始跨会话对比”。默认并排显示四层记忆和Deep Agents的回答、实际记忆继承、实时耗时和累计token。“更多对比设置”可选择重新学习或增加无记忆对照。

再次测试持久记忆时，只重复第2、3步，使用同一份保存记忆。Deep Agents会复用已保存的AGENTS.md，学习调用数为0。

“查看四层记忆”可进入各层的输入、输出和来源；页面右上角“高级详情”保留原有SQL编辑、数据库、版本管理和完整轨迹。“返回简明演示”可回到三步流程。

## 高级详情中的完整操作（可选）

双击 `打开热量选餐.cmd`，进入 <http://127.0.0.1:8010/?view=meal>。日常操作均在前端完成。

1. 首次使用可点击“初始化专用数据库”。已有库直接复用，不重建。
2. 当前会话输入：

   > 我不吃辣，午饭预算73块，热量470到610千卡。

   点击“保存偏好并整理记忆”，系统保存L1原话、L2结构化条件及L3主题，并自动创建不可变的记忆版本。
3. 在“给当前记忆保存一个名字”中填写“清淡午饭 · 73元”，点击“保存当前记忆版本”。
4. 在“新会话加载哪份记忆”中选择这份记忆，点击“新建会话”。当前会话ID改变，原先四层记录继续保留。新的会话不复制旧会话聊天全文。
5. 在新会话仅问：

   > 明天中午吃什么比较合适？

   点击“读取记忆并生成 SQL”。参数应包含73元、470～610千卡、不辣。打开“实际注入上下文”，查看所选记忆ID、笔记来源及当前会话历史；首次提问时历史为零。
6. 点击“执行 SQL 并计算”，查看推荐、所有候选状态、淘汰原因和热量明细。点击来源ID可沿查询结果、SQL、L4上下文、主题、笔记回到原话。
7. 在“当前会话”下拉框切换回旧会话，可恢复其SQL与执行结果；刷新保留当前会话、草稿和SQL。
8. 选择“不加载历史记忆（对照）”新建会话，同样提问。界面明确标注未加载个人偏好，查询使用演示默认参数（120元、600～700千卡、不辣）。历史记忆并未删除，仍可重新选择。
9. 想验证版本隔离，可在一个会话保存500～600千卡的新偏好。此会话会使用新记忆版本；其他会话仍使用它们先前选中的版本。

“独立空白空间”创建全新的记忆空间。之前使用此按钮创建的空间可在“记忆空间”下拉框重新选择；同一空间内的会话共享可选的保存版本。
升级前的有效饮食记忆会自动登记为“迁移前已保存的饮食记忆”，原始记录、SQL、笔记及上下文不会删除。
L1/L4历史经历继续保留，L2/L3的当前有效状态由所选记忆版本确定；新的请求重新生成L4，而不是直接复用旧请求。

## 跨会话对比与运行统计

切换“Deep Agents 对比”，点击“开始跨会话对比”。

- 四层组直接加载所选笔记和主题版本，不重新学习原话。
- Deep Agents 默认首次学习并保存磁盘AGENTS.md；再次选择相同记忆版本测试新会话时，直接复用文件，学习调用数为0。也可选择“本次重新学习原话”。
- 可勾选“不加载记忆”对照组。建议用73元、470～610千卡这类与演示默认值不同的条件，避免把默认值巧合当作记忆成功。
- 每组从实际开始时独立计时，运行中显示当前阶段、耗时和已完成调用返回的累计token；尚未返回用量的调用显示等待，不估算。
- 完成后保留总耗时、总token、学习/回答调用次数、学习/回答token、工具次数和实际加载的记忆内容。
- token来自提供方返回的输入与输出合计；缺失统计如实标为未提供或部分统计。排队等待其他组的时间不计入本组运行时长。
- 分别检查“SQL计算核对”和“记忆条件核对”：前者验证热量结果，后者将实际SQL参数与选定记忆及本轮明确覆盖逐项比较。无记忆组即使参数巧合相同，也不作为记忆证据。
- 统一全候选统计与工具实际返回行数分别展示，避免因SQL过滤差异误判。

Deep Agents只将保存的记忆文件复制进新回答目录，使用全新checkpoint和聊天thread，不复制旧对话。模型请求、记忆读取、工具及统计都保存在运行轨迹。
两组均生成对 `evaluated` 的最终SELECT，工具统一拼接同一份已核验公式CTE，避免让对比中的公式重写差异干扰记忆测试。完整实际执行SQL与模型生成的部分均保留。

## 数据隔离

仅使用以下专用目录：

```text
E:\memory_demo\data\meal_lab\
  meal_catalog.sqlite3          模拟业务库
  memory.sqlite3                本场景记忆、任务和事件
  catalog-reproducible.sql       可重建模拟业务库的完整SQL
  executions\<run-id>\          单次执行的只读数据快照
  comparisons\<run-id>\         两组对比共用的数据快照与独立记忆
```

不访问DBeaver的连接配置、凭据或其他数据库。新模块不读写原演示的 `data\memory.sqlite3`。
程序只在明确初始化时创建业务库；后续业务查询以SQLite URI `mode=ro`连接，开启 `query_only`，并通过authorizer限制为允许表及函数上的只读查询。
创建文件时验证应用标识；发现同名外部数据库则拒绝访问，不覆盖。

SQL执行前通过SQLite backup复制本场景业务库到本次运行目录。查询、独立结果核对和食材明细使用同一个快照，历史证据不会随DBeaver后续编辑变化。

## DBeaver 连接

1. 新建数据库连接，选择SQLite。
2. 数据库文件选择 `E:\memory_demo\data\meal_lab\meal_catalog.sqlite3`。页面“已连接专用本地库”也显示绝对路径，并提供复制按钮。
3. 在SQL编辑器粘贴页面生成的SQL，启用命名参数。参数前缀为 `:`；执行时填入页面“绑定参数”的同名值：

   | 参数 | 示例 | 含义 |
   |---|---|---|
   | `budget` | 120 | 每份最高价格，元 |
   | `kcal_min` / `kcal_max` | 600 / 700 | 允许热量区间 |
   | `min_spice` / `max_spice` | 0 / 0 | 允许辣度区间：0不辣，1微辣，2辣 |
   | `meal_period` | dinner | 记忆餐次：breakfast / lunch / dinner / any，用于会话条件校验 |
   | `recommend_count` | 3 | 展示的不同饭菜数量；不是 SQL 候选条数 |
   | `as_of` | 取页面保存值 | 价格、配方和营养版本的计算日期 |
   | `name` | 空字符串 | 菜名或别名限制；消歧后使用所选具体菜名 |
   | `offer_id` | 空字符串 | 可选的单个售卖项目 |
   | `limit` | 200 | 返回行数 |

4. `name`、`offer_id`不筛选时填写空字符串，不能填写SQL NULL。需要复现历史执行时，打开其结果来源的“完整输入与元数据”，使用保存的参数，并连接其中 `db_path` 指向的执行快照。
5. 对比 `offer_id`、`recipe_ids`、`price_ids`、热量上下界及status。

页面可以下载建表SQL、完整建库SQL和查询模板。完整建库SQL只在新建空白库使用，不在已有库重复执行。
当前SQLite驱动需支持窗口函数（SQLite 3.25及以后）。应用使用Python自带的SQLite。

命名参数与SQLite文件连接方式依据 [DBeaver SQL执行文档](https://dbeaver.com/docs/dbeaver/SQL-Execution/) 和 [SQLite连接文档](https://dbeaver.com/docs/dbeaver/Database-driver-SQLite/)。

## 数据库与计算口径

14张表，3个门店（含停用示例）、50道菜、150个规格、80种食材、92条营养版本、58个配方版本、300条历史价格、20组套餐，以及别名、单位和数据字典。

字段命名保留模拟遗留库风格，如 `nm`、`qty`、`amt`、`mult`。表间外键、字段解释、单位、版本区间和样例数据在“数据库与口径”中可查。
全部营养和经营数据均为合成模拟数据，不宣称来自营养成分权威数据库。

公式版本 `meal-energy-v1`：

```text
每份热量 = Σ[同口径可食克数 / 100 × (4P + 9F + 4C)]
           + 9 × 每份额外用油克数 × 留存率
```

- 营养值单位为 g/100g，重量口径为 raw 或 cooked。
- 先执行单位换算；仅毛重乘可食比例；生转熟乘出成率、熟转生除出成率。
- 整配方的食材及额外用油均除以配方产出份数，再乘售卖规格倍率和套餐数量。
- 营养数据中的基础脂肪不包含配方额外用油，后者不作为食材重复加入。
- 版本采用 `[valid_from, valid_to)`，相同项目取当前最新版本；停用项目不参与推荐。
- 状态判断使用未舍入值，结果热量保留一位小数。
- 完整落入目标区间且满足预算和辣度为pass；部分重叠为uncertain；明确超出为fail；关键数据缺失为unknown。

## 模型与确定性计算的边界

模型真实执行条件提取、问题解析和最终SELECT生成。常用偏好表述再由确定性规则校准；数字与摘录核对，避免模型猜测未表达的条件。完整请求与响应保存在运行轨迹，不展示内部推理链。

多表关联、版本筛选、单位转换及公式计算来自可审查的CTE模板（`sql/meal_lab/query.sql`）；模型生成最后的SELECT，后端拼接成完整SQL。页面明确标出这一区别。
主题表示采用确定性编译，保持笔记ID及当前版本关系，不声称这一步使用了模型。

SQL允许编辑，但最多单条SELECT/WITH，执行期限2秒，普通查询最多返回500行；关键内部明细单独使用有界上限。
系统用标准公式查询对每一条返回结果进行独立核对。自由探索SQL可以返回任意允许表上的查询结果，但未通过标准输出核对时不会用来推荐。

最终推荐文字由已核验SQL结果确定性渲染，菜名、热量、价格和辣度均来自实际结果。Deep Agents原始模型回答另存为 `model_answer`，工具与模型轨迹保留。结果展示依据的上下文标记 `sent_to_model=false`，不会冒充模型注入；SQL规划时的实际注入上下文仍单独可查。引用校验不等于完整事实审计。

## 保存与新会话演示（条件规则 v2）

1. 第1步输入名称“晚饭偏好”，原话：“我特别喜欢吃辣，晚饭预算500块，热量尽量控制在1000千卡。简单推荐三种就行。”点击“保存这份记忆”。默认独立保存，不借用旧午饭条件。只有确实要修改原偏好时，展开保存方式并勾选保留未提及条件。
2. 第2步选择“晚饭偏好”，点击“新开会话并加载”，只问“晚上吃什么好”，点击测试。应看到晚饭、预算上限500元、热量≤1000千卡（未设下限）、喜欢辣（仅选有辣）。500和1000均为上限，不要求价格或热量接近它们。
3. 查看实际注入、SQL参数与菜品来源。新会话不复制上一会话聊天全文；同一新会话继续聊时会使用本会话历史。
4. 第3步在“选择用于两组对比的记忆”中选择“晚饭偏好”，保持同一个问题，点击“开始跨会话对比”。即使当前处于无记忆对照会话，也会自动新开会话并加载选定记忆，无需返回第2步。未选记忆或问题为空时，页面说明不能开始的原因；空间里没有保存记忆时，可点击“去保存一份记忆”。首次Deep Agents学习AGENTS.md；下次复用文件，用新的checkpoint查询。分别展示实际耗时与服务返回token。展开条件明细可逐项核对。

无记忆对照：第2步选择“不加载记忆（用于对照）”。更换选择后会立即收起旧结果，提示“尚未应用”。直接点击“新开无记忆会话并测试”，系统先创建不绑定个人记忆的新会话，再在该会话测试；也可以先点击“新开无记忆会话”，再点“测试无记忆对照”。仅问“晚上吃什么好？”时，结果应明确标注演示默认预算120元、600～700千卡、不辣，个人记忆ID为空、偏好来源列表为空。重新选回“晚饭偏好”后，点击“加载所选记忆并测试”可自动创建另一新会话恢复500元、喜欢辣等条件。新建失败会保留待应用选择并阻止向旧会话发送测试，不会回退到旧会话继续回答。

“喜欢辣”要求最低辣度1；“能吃辣”允许0～2；“不吃辣”只允许0；“只吃微辣”只允许1。不设置热量下限时实际参数为0，不从旧记忆补齐。未指定的预算/上限使用演示技术边界10000，界面显示未设条件。若想“接近1000千卡”，请明确说900～1000千卡。

推荐先满足全部硬条件，再优先主餐、标准份，按菜品去重，同菜不同份量不占用多种推荐名额；不会为凑数量放宽条件。条件冲突、午晚饭记忆混用、目前无法核验的禁忌/低盐少油等要求会明确报错。无符合项时显示没有找到，不显示推荐成功。

旧版保存记忆会先备份至 `data/meal_lab/backups/`，再从原始偏好生成校准新版本，并更新会话绑定。旧快照、原话和运行记录保留；旧规则结果标记历史，需重测。无法可靠校准的旧版本会阻止继续使用。

Deep Agents SQL工具会检查包括未设置条件在内的实际传参；错误调用被拦截并记录，模型可重读AGENTS.md，必要时按需检索该版本保存时的偏好原话。纠错调用及检索次数在结果与轨迹中展示，相关耗时/token全部计入。回查来源后通过不能解释为仅凭摘要直接记住。

## Deep Agents 对比

真实调用 `deepagents.create_deep_agent`，使用FilesystemBackend、AGENTS.md、SQLite checkpointer和专用只读SQL工具。
首次建立文件记忆时，每条偏好在独立学习thread中写入；后续新会话直接复用已保存文件。callback保存模型调用和工具输入输出。
四层分支直接读取选定的不可变记忆版本；各组使用本次比较复制的同一业务库快照。
调用次数、token、耗时包括学习和回答。工具、框架提示和学习预算不同，不作为等预算性能排名；未执行SQL或调用失败会明确显示。
